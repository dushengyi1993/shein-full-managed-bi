# 全托 BI 门户信息架构与首版页面规划

最后更新：2026-07-20

## 1. 设计依据

全托门户沿用半托 BI 已验证的页面骨架：固定侧栏、顶部全局筛选、首页总控、业务域子页、系统健康和受控自动化入口。首版继续使用当前原生 HTML / CSS / JavaScript 和同源只读 API，不引入新的前端框架。

本次不复制半托业务指标。半托首页已有成交额、订单、售后、利润、流量、库存等事实域；全托当前只确认了 SKU 销量数量接口，应用、权限包、店铺授权和接口探针仍须分层判断。因此页面可以先建立完整的信息架构，但只有销量域展示数量事实，其他业务域必须展示接入状态、所需证据和空状态，不能用示例金额或推导值填充。

## 2. 当前页面问题

- 没有全局导航，页面只有权限条、四张数字卡和两个排行表。
- 首页没有回答“今天先看什么”，也没有业务域入口和数据健康状态。
- 排行、权限和系统状态混在一个页面，无法下钻。
- 缺少店铺、SKU 和时间范围筛选。
- 示例数据虽然有标签，但主体数字过于突出，仍容易被误读为真实经营数据。
- 没有把“应用审核通过、权限包审核、店铺授权、接口探针、事实入仓”拆成独立阶段。
- 视觉是通用统计卡片，没有继承半托 BI 的侧栏、工具栏、矩阵、排行和状态语言。

## 3. 全局页面骨架

### 固定侧栏

侧栏负责一级导航、当前数据环境和关键接入状态。桌面端固定在左侧，窄屏变为顶部横向导航。

导航顺序：

1. 总控驾驶舱
2. 销量分析
3. 商品中心
4. 合规中心
5. 备货履约
6. 库存管理
7. 财务对账
8. 自动化运营
9. 系统健康

### 顶部全局筛选

所有可读取销量事实的页面共用：

- SKU / 商品名搜索；
- 店铺筛选；
- 时间口径：今日、昨日、近 7 日、近 30 日；
- 清空筛选；
- 当前数据环境与更新时间。

现有销量接口只提供预聚合窗口，不能把它伪装成任意日期范围。未来接入日粒度事实后，再升级为与半托一致的双日历。

## 4. 首页放什么

首页只回答五个问题，不放长明细：

1. **数据能不能看**：示例 / 实时、更新时间、只读状态。
2. **接入走到哪一步**：应用审核、销量权限包、店铺授权、接口探针、事实入仓。
3. **销量规模如何**：今日、昨日、近 7 日、近 30 日销量数量。
4. **哪里最值得先看**：销量最高店铺、销量最高 SKU、权限或数据阻断点。
5. **去哪里处理**：销量、商品、备货、库存、财务、自动化运营的快捷入口。

首页下半部分保留：

- 销量趋势；没有日粒度数据时显示明确空状态；
- 店铺销量 Top 榜；
- SKU 销量 Top 榜；
- 业务域接入地图。

长表、完整排行、字段证据和操作流程全部下沉子页。

## 5. 子页面放什么

| 页面 | 回答的问题 | 首版内容 | 当前数据边界 |
| --- | --- | --- | --- |
| 销量分析 | 哪家店、哪个 SKU 在当前窗口卖得更多？ | 时间口径、店铺表、SKU 表、筛选与排行 | 已支持 SKU 销量数量；缺数保持空值 |
| 商品中心 | 哪些 SKU 已进入全托商品身份与销量映射？ | SKU 销量清单、商品身份接入流程、映射状态 | `number-list` 和完整商品主数据待探针 |
| 合规中心 | 哪些商品资料或证书需要处理？ | 权限/数据接入说明、未来字段和动作边界 | 当前无合规事实，不展示伪造风险数 |
| 备货履约 | 哪些采购、备货、到货任务需要跟进？ | 接入步骤、所需单据、销量需求信号入口 | 当前无备货/采购单事实 |
| 库存管理 | 实际可用库存与销量速度是否匹配？ | 库存域接入说明、销量需求信号 | 不用销量反推库存，不把未知当零 |
| 财务对账 | 平台结算、费用和回款是否一致？ | 财务域接入说明、会计期间和对账边界 | 当前无金额、结算、成本或利润事实 |
| 自动化运营 | 哪些动作可自动识别、预演并受控提交？ | 只读建议、六步执行生命周期、能力门禁 | 写动作默认关闭；权限、预演、确认、回读缺一不可 |
| 系统健康 | 今天的数据和权限能否放心使用？ | 数据集状态、五阶段接入表、能力清单、云端运行态 | 明确生产 / 示例 / 未授权状态 |

## 6. 全托与半托的差异

- 半托已有订单、售后、流量、评价、营销和利润事实；全托首版不展示这些指标。
- 全托一级业务域按应用申请范围组织：商品管理、商品合规、备货管理、库存管理、财务管理。
- 半托“营销中心”不直接复制到全托。只有确认全托对应权限、平台控制边界和真实字段后，才决定是否单独建设。
- 全托自动化优先围绕商品资料、合规、备货履约、库存和财务复核；任何写动作都必须保留权限检查、dry-run、明确确认、审计和结果回读。
- 全托与半托数据仓库、应用凭据、权限探针和事实表保持隔离。

## 7. v0.2 实现范围

- 重做为与半托同一设计家族的固定侧栏和顶部筛选布局；
- 使用 hash 路由实现九个一级页面，不改变当前服务器的安全路由；
- 总控、销量分析、商品中心和系统健康使用现有只读销量数据；
- 合规、备货、库存、财务和自动化运营提供真实边界与接入状态，不伪造业务数；
- 数据请求失败时在首屏显示错误，并保留重试；
- 示例数据在侧栏、顶部和内容区持续标记；
- 桌面和移动视口均可用；
- 保持 CSP、只读 HTTP 方法限制和敏感指标白名单。

## 8. 验收标准

- 首页不再出现完整长表，能在首屏看清数据状态、接入进度和四个销量指标；
- 九个一级导航均可打开，当前页有明确高亮；
- 店铺、SKU 搜索和时间口径会同步影响可用销量视图；
- 任何未接入业务域都不会显示虚构的零、金额、订单或利润；
- 示例数据与实时数据在视觉和文案上不可混淆；
- `/health`、`/api/dashboard`、静态资源、安全头和未知路径契约继续通过测试；
- 浏览器无控制台错误，桌面首屏与窄屏完成视觉验收。
