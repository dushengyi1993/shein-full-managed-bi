# 全托 BI 门户信息架构与首版页面规划

最后更新：2026-08-10

## 1. 设计依据

全托门户沿用半托 BI 已验证的页面骨架：固定侧栏、顶部全局筛选、首页总控、业务域子页、系统健康和受控自动化入口。首版继续使用当前原生 HTML / CSS / JavaScript 和同源只读 API，不引入新的前端框架。

本次不复制半托业务指标。半托首页已有成交额、消费者订单、售后、利润、流量等事实域；全托首版使用 SKU 销量、商品、采购、交付、库存、缺货和 Webhook 各自的只读事实。没有独立事实的数据域仍只展示接入状态、所需证据和空状态，不能用示例金额或推导值填充。

门户为运营导向，不是官方后台的复刻：只保留能指导运营的页面与字段；没有独立运营价值的入口不单独建页，也不复制官方后台的分组层级。

## 2. 已解决的页面问题

- 固定侧栏、顶部筛选、业务域下钻和系统健康已经拆分；
- 首页回答“今天卖了多少、趋势如何、哪家店和哪个标准商品领先、数据是否可信”；
- 示例、空库、合法零销量、缺权限、部分覆盖与真实数据有不同文案；
- “应用审核、权限包、店铺授权、接口探针、事实入仓”保持为五个独立阶段；
- 员工默认读取全店数据，负责人/店铺/商品只作为全局筛选；
- 桌面与 390px 窄屏均无横向溢出。

## 3. 全局页面骨架

### 固定侧栏

侧栏负责一级导航、当前数据环境和关键接入状态。桌面端固定在左侧，窄屏变为顶部横向导航。

导航为 9 个直接运营入口，不设二级分组（桌面端纵向平铺，窄屏为可横向滚动的同一平铺列表）：

1. 总控驾驶舱
2. 商品经营
3. 库存与备货
4. 采购履约
5. 退货与质量
6. 财务与结算
7. 营销机会
8. 运营待办
9. 数据与系统

不再提供“订单管理”可展开分组。旧订单管理九子页（发货订单、发货单列表、
备货记录、运单报表、退货申请、退货列表、收货/退货异常、增值服务列表、
质检报告）的 hash 路由保留为兼容深链接，供历史书签与外部引用继续打开，
但不在主导航中出现；旧 `#fulfilment` 等入口继续打开原只读兼容页，同时
按数据域高亮对应的新主入口
（发货/运单/收货归采购履约，退货/异常/质检归退货与质量，备货记录归
库存与备货），不复制或倒退既有实现。

侧栏 DATA HEALTH 卡片（数据状态、经营日报、财务明细、库存台账、实际
结算、页面底稿、自动更新）移入“数据与系统”页，不再常驻侧栏占用首屏。

### 顶部全局筛选

所有可读取销量事实的页面共用：

- 标准货号、SKC、SKU / 商品名搜索；
- 负责人筛选（只影响视图，不限制读取）；
- 店铺筛选；
- 时间口径：今日、昨日、近 7 日、近 30 日；
- 清空筛选；
- 当前数据环境与更新时间。

现有销量接口只提供预聚合窗口，不能把它伪装成任意日期范围。未来接入日粒度事实后，再升级为与半托一致的双日历。

## 4. 首页放什么

首页只回答五个问题，不放长明细：

1. **数据能不能看**：示例 / 实时、更新时间、只读状态。
2. **接入走到哪一步**：应用审核、销量权限包、店铺授权、接口探针、事实入仓。
3. **销量规模如何**：今日、昨日、近 7 日、近 30 日销量数量。
4. **哪里最值得先看**：销量最高店铺、销量最高 SKU、权限或数据阻断点。
5. **去哪里处理**：商品经营、库存与备货、采购履约、退货与质量、财务与结算、营销机会、运营待办和数据与系统的快捷入口。

首页下半部分保留：

- 销量趋势；没有日粒度数据时显示明确空状态；
- 店铺销量 Top 榜；
- 标准商品销量 Top 榜；
- 业务域接入地图。

长表、完整排行、字段证据和操作流程全部下沉子页。

## 5. 子页面放什么

| 页面 | 回答的问题 | 首版内容 | 当前数据边界 |
| --- | --- | --- | --- |
| 总控驾驶舱 | 今天的数据能否放心看、销量规模如何？ | 经营脉搏、四窗口销量、趋势、Top 榜与接入地图 | 只有已入仓事实参与；缺数保持空值 |
| 商品经营 | 哪些店内货号属于同一标准商品、哪个 SKU 卖得更多？ | 标准商品与店内身份、待归并货号、四窗口销量与排行 | 店内强键；跨店只接受强证据；只有销量件数 |
| 库存与备货 | 哪些 SKU 缺货或库存覆盖不完整？ | 全托 PI / JI、仓库库存、缺货建议与对账、备货记录；VI 仅作兼容诊断 | 请求集合来自稳定销量清单；备货记录按既有覆盖门禁展示 |
| 采购履约 | 采购单、发货、运单、收货各节点处于什么状态？ | 采购单与行项目、发货订单、运单报表、收货节点、时间和字段覆盖 | 当前快照与阶段信号，不是漏斗；未知数量不补零；只读无 SHEIN 写 |
| 退货与质量 | 有哪些退货信号、质检结果如何？ | 退货申请、退货列表、收货/退货异常、质检报告 | 按页计算店铺覆盖；缺店保持未知、不补零、不伪造 |
| 财务与结算 | 平台结算、费用和回款是否一致？ | 会计期间和接入边界 | 当前无金额、结算、成本或利润事实 |
| 营销机会 | 全托有哪些可确认的营销入口？ | 已知权限与平台控制边界 | 半托营销中心不直接复制；确认权限、控制边界和真实字段后才单独建设 |
| 运营待办 | 哪些问题可形成待办候选？ | 只读候选池、原因和证据 | 所有动作控件关闭 |
| 数据与系统 | 今天的数据和权限能否放心使用？ | 数据健康（数据状态、日报/财务/库存/结算回读、页面底稿、自动更新）、Receiver/Worker 心跳、队列、订阅回读、覆盖与具体原因 | 至少一次语义；订阅写入关闭；不用空队列或合法零销量制造误报 |

采购履约并列展示采购与发货各自最新物化快照的阶段状态，不是转化漏斗；
页面分别标注两侧事实时间，不把两个文件冒充同一事务快照。采购单、发货、运单、
收货各节点只并列呈现各自的数量与明细，不做跨阶段率或转化推导；任一节点
未知数量保持未知、不补零，也不因其他节点有数而推断。页面只读，不提供
任何 SHEIN 写操作。

## 6. 全托与半托的差异

- 半托已有消费者订单、售后、流量、评价、营销和利润事实；全托首版不展示这些指标。
- 全托一级导航按运营动作组织为九个直接入口，不再按官方后台分组复刻，也不保留“订单管理”二级分组。
- 半托“营销中心”不直接复制到全托，仅以“营销机会”入口展示已知权限与平台控制边界；只有确认全托对应权限、平台控制边界和真实字段后，才决定是否纳入运营页面。
- 全托自动化优先围绕商品资料、合规、采购履约、库存和财务复核；任何写动作都必须保留权限检查、店铺归属、dry-run、明确确认、审计和结果回读。
- 全托与半托数据仓库、应用凭据、权限探针和事实表保持隔离。

## 7. v1 实现范围

- 重做为与半托同一设计家族的固定侧栏和顶部筛选布局；
- 使用 hash 路由实现 9 个一级入口；旧订单九子页 hash 仅作兼容深链接，继续渲染原只读页并高亮对应新主入口，不改变服务器安全路由；
- 总控、商品、库存、采购、退货质量、财务、营销边界、运营待办和数据系统使用各自的只读事实；
- 财务、营销和运营待办提供真实边界与已有事件，不伪造业务数；
- 数据请求失败时在首屏显示错误，并保留重试；
- 示例数据在内容区显著标记；生产正式数据不显示示例提示；
- 桌面和移动视口均可用；
- 保持 CSP、只读 HTTP 方法限制和敏感指标白名单。

### 7.1 独立采购查询与快照更新

- `/api/procurement` 是认证后的独立只读查询面，服务端执行负责人、
  店铺、文本、状态、关注类型、排序和有界分页；Portal 仍然不持有
  数据库连接或 SHEIN 凭据。
- 查询范围是物化器写入 `dashboard.json` 的采购状态和关注明细。响应
  同时返回 `total / returned / truncated`，页面必须使用“已物化范围命中”
  描述筛选结果；源明细截断时禁止称为仓库全量。
- `/api/events` 是认证后的同源 SSE 更新流。服务器只监听
  `dashboard.json` 的原子提升并广播无路径、无业务值的版本通知；一个
  共享 watcher 服务所有连接，最后一个客户端断开后释放 timer。
- 浏览器收到版本通知后重新请求 `/api/dashboard` 和当前采购查询。
  页面使用“快照自动更新”，不得称为 SHEIN 实时连接；事实时间和业务
  日期仍以响应字段为准。

### 7.2 独立销量查询与经营脉搏

- `/api/sales` 是认证后的独立只读查询面。负责人、店铺、搜索、商品
  身份、近 7 日/此前 23 日动量、排序以及店内商品/标准商品各自分页均
  在服务端执行；重复参数、未知负责人和越界页大小失败关闭。
- 查询只覆盖 `dashboard.json` 已白名单化的店铺、店内 SKU 和标准商品
  排行。响应分别返回物化命中数和 ranking `returned / total /
  truncated`；页面只能称“已物化范围命中”，不能称仓库或 SHEIN 全量。
- 首页“经营脉搏”不新增业务事实：它把已有销量窗口、采购/交付关注、
  库存风险、排行与数据质量压缩成四个可下钻判断。金额、消费者订单和
  不完整窗口不参与推导，合法零、未知、部分覆盖保持不同文案。

### 7.3 订单只读工作区与兼容深链接

- `/api/orders?page=<pageId>` 是认证后的统一只读查询面；筛选、排序和分页均在服务端执行，
  未知参数、重复参数和写方法失败关闭。
- 该查询面继续服务旧订单九子页：发货/运单/收货节点经深链接在“采购履约”下打开，
  退货申请、退货列表、收货/退货异常、质检报告经深链接在“退货与质量”下打开，
  备货记录经深链接在“库存与备货”下打开；增值服务列表等无独立运营价值的旧页
  仅保留深链接解析与数据边界，不进入主导航。
- 完整页不占用首屏展示技术门禁；部分覆盖页可展示已验证店铺的业务行，但只能提示
  “当前展示 X/25 家，Y 家暂无数据”，缺店保持未知。完全不可用的页面返回 `503`；
  `PAGE_GATE_FAILED`、`SESSION_GATE_FAILED`、endpoint 和店铺长名单只保留在后端审计与日志，
  不进入业务 UI。
- 页面只允许查询和展开脱敏详情，不提供打印、取消、发货、备货、确认退货、签收、复议、
  自动确认等平台写操作。
- `order-management.json` 与核心 Dashboard 文件在同一 staging/promote 链路中原子提升；
  任一覆盖、分页、总数或去重门禁失败时保留旧版本，禁止发布半套快照。

## 8. 验收标准

- 首页不再出现完整长表，能在首屏看清数据状态、接入进度和四个销量指标；
- 9 个一级入口直接平铺均可打开，当前页有明确高亮；旧订单深链接仍能解析到对应页面；
- 负责人、店铺、商品搜索和时间口径会同步影响可用视图；
- 任何未接入业务域都不会显示虚构的零、金额、订单或利润；
- 示例数据与实时数据在视觉和文案上不可混淆；
- `/health`、`/api/dashboard`、`/api/procurement`、`/api/sales`、`/api/orders`、`/api/events`、
  静态资源、安全头和未知路径契约继续通过测试；
- 浏览器无控制台错误，桌面首屏与窄屏完成视觉验收。
