# 全托 BI 首版能力边界

## 当前支持

- 全托管店铺主数据与逐店隔离；
- “销量查询”权限包的只读探针历史；
- OpenAPI 抓取批次、错误、分页结果数量和脱敏响应证据；
- 店铺内 SKU / SKC / SPU 身份归并；
- 指定时间窗口、指定观察时点的 SKU 销量**数量快照**；
- 店铺和商品维度的最新销量数量聚合；
- 数据新鲜度、来源批次和指纹追溯；
- 本地开发、数据库迁移、契约校验和 Git 版本管理。

“应用审核通过”“店铺完成授权”“手动申请了销量权限包”和“销量接口实际可读”是四件不同的事。首版只有最新的只读探针返回明确业务成功，才把该店视为 `GRANTED`；缺权限或抓取失败必须显示为缺数，不能显示为零销量。

## 当前明确不支持

- 销售金额、GMV、成交额、币种换算；
- 订单数量、订单明细、订单状态和消费者信息；
- 退款、退货和取消订单口径；
- 供货价、平台结算、费用、税费、回款和发票；
- 成本、毛利、净利、利润率；
- 采购单、备货单、到货、入库、补货建议；
- 实时库存、履约时效和仓库作业；
- 跨店统一商品主数据；
- 任何商品、库存、采购、财务或营销写操作；
- 云端部署与半托生产事实源切换。

因此首版页面和 API 只能使用“销量数量”或“件数”措辞，不能写“销售额”“订单量”或“利润”。也不能用销量乘当前价格推导金额，因为价格和销量窗口并不具备同一历史口径。

## 全托与半托隔离

- 全托使用独立仓库迁移、表名、配置和应用凭据；
- 不复制半托大型 schema，不把半托 API 字段默认当作全托字段；
- 不把相同公司主体理解为相同应用、权限、店铺或数据授权；
- 如未来需要跨模式分析，只能在两个事实源各自完成探针、对账和质量检查后，通过新的只读映射层联合，不能直接互写事实表。

## 后续独立数据域

财务和采购必须各自设计独立域，不向销量事实表追加“顺手可用”的列：

- **财务域**：结算单、费用项、税费、回款、币种与汇率，拥有独立事实粒度和会计期间；
- **采购域**：采购单、备货、到货、入库和补货，拥有独立单据状态机与数量口径；
- **订单域**：只有在获得独立订单权限并确认个人信息处理边界后再设计；
- 各域只通过稳定的店铺、SKU / 商品映射关联，并保留来源批次和对账状态。

新域上线前必须分别完成：官方接口确认、字段样本留证、权限探针、时间与状态口径、幂等策略、脱敏规则、历史回填方案和逐店对账。

## 安全与发布门槛

- 仓库不得包含数据库密码、OpenAPI secret、token、cookie、签名或浏览器 Profile；
- raw 与 ops JSON 在写库前必须脱敏，错误日志也遵守同一规则；
- 本地探针不得执行写接口；
- 数据库迁移必须在空库和重复执行场景验证；
- 云端扩容完成后仍需容量预算、备份恢复演练、最小权限账号和回滚方案；
- 未完成逐店探针与事实对账前，不宣称全托 BI 已成为生产事实源。
