# 半托迁移到飞牛 + 新云服务器转发：全托经验交接

整理日期：2026-09-08。供半托任务规划和实施参考，本文件本身不执行半托迁移。

依据：全托 9 月 6 日飞牛切流记录、9 月 8 日边缘迁移记录及收尾证据。下述已完成结果是当时的验收记录，不代表重新检查了此刻服务器状态。半托的服务、数据库、店铺和端口必须重新盘点，不能照抄全托实例。

## 1. 目标架构与本次实际范围

全托分两段完成：先把业务、数据库、授权服务和调度迁到飞牛；再把旧云入口和 OpenAPI 固定出口迁到新云。半托也建议分段验收，降低故障定位和回滚难度。

```text
用户 / SHEIN 回调
  → 半托域名 HTTPS
  → 新云 43.165.185.3（TLS / 反向代理）
  → 新云回环端口 → 飞牛主动建立的 SSH 反向隧道
  → 飞牛半托 Portal / Webhook / 授权等服务 → 飞牛数据库

飞牛半托 OpenAPI 客户端
  → 飞牛专属回环代理端口 → SSH 本地转发
  → 新云受限 CONNECT relay → SHEIN OpenAPI
  → 平台看到固定出口 43.165.185.3
```

公网入口与 OpenAPI 出口是两条独立链路，都要验收。业务迁入飞牛不等于出口自动变成新云 IP。

普通 WebAPI 和浏览器网络在全托方案中保留办公室直连；没有设置全局 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY。半托先核实自己的网络依赖，再决定哪些请求需要固定出口。

### 2.1 用户确认的磁盘方案与资源建议

用户已明确：半托与全托继续共用现有机械硬盘，做好备份。采用半托独立 VM 的建议，不把新增 SSD 作为迁移前提。本次只更新交接文档，没有创建 VM、调整全托资源或配置备份任务。

2026-09-08 17:12—17:15 的只读现场检查依据：

- 飞牛 CPU 为 Ryzen 5 5600G，6 核 12 线程；系统可见内存约 27.3 GiB，当时 MemAvailable 约 4.3 GiB，ZFS ARC 约 6.2 GiB。
- 全托 VM 为 4 vCPU、12 GiB，内部可用约 10.4 GiB，但宿主 QEMU 进程 RSS 约 12.1 GiB；内部空闲不等于宿主已收回。
- 半托旧云为 2 vCPU、约 7.5 GiB。9 月 7—8 日整机十分钟采样最低可用约 4.1/3.8 GiB；最近登录维护任务内存峰值约 1.37 GiB。旧云还运行其他项目，整机占用不是半托独占占用；采样也可能漏掉瞬时峰值。晨间链路当时存在失败，不能当作完整正常负载验收。
- 全托虚拟磁盘位于 `/vol2/vm/pool/` 对应的 1 TB 机械盘，空间当时可用约 748 GiB。短采样出现磁盘忙碌 64%—84%、读写等待约 37—171 ms，这是短时观测，不代表全天平均。

目标规格建议如下，实施时先重新核实容量与负载：

| 资源 | 全托 VM | 半托新 VM |
| --- | --- | --- |
| CPU | 保持 4 vCPU | 4 vCPU，共享宿主算力 |
| 内存 | 建议由 12 调为 8 GiB；先核对重任务峰值并安排维护窗口 | 8 GiB |
| 数据磁盘 | 保留现有虚拟磁盘 | 独立数据虚拟盘，建议 200 GiB，放同一块 `/vol2` 机械硬盘 |

两台 VM 合计 16 GiB 配额后，系统可见内存剩余约 11.3 GiB 用于宿主、NAS 服务、ZFS 缓存、虚拟化开销和余量；这不是保证空闲的内存。半托系统盘另行计入容量预算，200 GiB 是数据盘建议。全托降配尚未实施，不能按已释放 4 GiB 启动新 VM；也不能未经检查就把宿主 ARC 全部当作随时可占用的空间。

**后续实做更新（2026-09-08 17:27）：** 用户授权后，全托已正常关机，在飞牛管理界面从 12 GiB 改为 8 GiB 并开机。前文“尚未降配”为历史状态。宿主回读 Max/Used memory 均为 8388608 KiB，4 vCPU 和原磁盘保持不变，VM 原 IP 192.168.1.79 正常；管理界面保存时自动重新生成了虚拟网络 interfaceid。数据库启动检查通过，Portal、授权、StoreLogin、新隧道、Webhook receiver/worker 已恢复。VM 系统可见约 7941 MiB，开机后可用约 7 GiB，无 swap 使用。配置前后备份及回读位于 `tmp/vm-memory-20260908/`。

本次开机曾出现 RTC/来宾时间解释相差 8 小时，NTP 已纠正系统时间；通过 daemon-reload 和重启受影响 timer 恢复正确排班，下一次实时任务为当日 18:02、会话续期为次日 00:30。未修改定时规则。后续开机需检查时间同步后的 NextElapse；RTC 配置一致性仍需单独处理，不能认为此次排班修复已永久解决启动时钟差异。

| 资源 | 对其他系统的影响 |
| --- | --- |
| CPU | 通常共享调度。4 vCPU 是虚拟处理器数量，不等于永久独占 4 个物理核心；空闲时算力可供其他任务使用。实际 CPU 配额、绑核和隔离设置需另查。 |
| 内存 | 应按 VM 配额做容量预算。内存气球等回收机制必须实际配置并验证，不能假设 VM 内部空闲会自动全部归还宿主。 |
| 磁盘容量 | 预分配可能提前占用；精简分配一般随写入增长。创建前检查镜像格式、预分配、ZFS 配额/预留和快照策略；同时核算逻辑容量与物理剩余空间。 |
| 磁盘性能 | 同一物理盘的读写能力仍然共享。独立 VM、独立虚拟盘能隔离管理范围，不能消除 I/O 竞争。 |

### 2.3 共用机械盘的运行与备份要求

- 两套系统分别使用独立虚拟盘、数据库和备份目录，不共用数据库文件。保持现有全托数据盘和权限不变。
- 先读取两边真实排班，再错开数据库备份、恢复演练、大物化和批量扫描。分 VM 后原有 `/run` 文件锁彼此不可见，不能假设原共机锁继续协调两套系统；需要明确共享盘重任务的跨 VM 排班或互斥办法，保留每项业务唯一调度入口。
- 迁移验收覆盖两套系统同时运行的实际时段，检查 I/O 延迟、队列、任务耗时和用户页面响应；不要仅以磁盘容量够用作为性能验收。
- 半托建立自己的数据库一致性备份，并覆盖业务配置、必要文件和受保护的授权材料。定期备份之外，迁移切流前保留可恢复基线；频率根据允许的数据损失窗口确定，若要求小于一天则不能只做每日备份。
- 备份至少保留到不同物理盘。现有 `/vol3` 是独立 500 GB 机械盘，当时可用约 312 GiB，可作为半托独立备份目录的候选；实施前核实容量、权限和全托保留策略，禁止覆盖全托备份。同一 `/vol2` 上的快照或副本不能替代异盘备份。
- 对备份设置明确保留周期、容量上限、失败提示和最近成功时间检查。至少完成一次隔离恢复，核验关键表/记录及应用读取，不能仅看备份文件存在或哈希正确。
- 异盘仍在同一飞牛中，不能覆盖整机损坏、失窃等情况；另一个设备或远端副本作为后续保护选项，不在本次文档更新中擅自创建或外传数据。

## 3. 推荐实施顺序与每步验收

### 第一步：只读盘点并确定切换、回滚边界

- 盘点业务入口、数据库及版本/扩展、文件存储、浏览器 Profile、授权凭据、任务队列、worker、timer/cron、锁、续期任务和外部回调。
- 记录当前发布版本、工作区改动、配置哈希、端口、服务依赖、调度规则、最近真实运行结果、DNS/NS、证书和其他项目入口基线。
- 确定旧端哪些组件写数据库、发平台请求或消费队列，列出停旧启新的严格顺序。同一个业务调度、队列或写入源只能有一个执行方。
- 写明可接受中断、数据截止点、失败恢复条件。备份保留权限和属主；不把密钥、Cookie、令牌放入普通报告。

验收：有一份明确的半托资源映射、写入者清单和可执行回滚计划，而不只是“服务器能 SSH”。

### 第二步：在飞牛准备候选环境并演练数据恢复

- 使用独立服务账户、目录、数据库和资源限额；部署锁定版本的运行时和业务代码，避免升级共享环境。
- 候选 timer/worker 默认不消费真实任务、不执行生产写入。核实 ConditionPathExists 等启动门禁；enabled 不代表 active。
- 按半托数据库特点选备份恢复或复制方案，先在隔离目标恢复，再校验表、关键记录、序列、索引、约束/触发器和版本兼容。
- 对持续变化的数据设计最终追平；不能用一次旧备份覆盖整个在线迁移窗口。
- 配置业务备份并做独立恢复验证。容量、磁盘健康、办公室网络/供电和恢复时间单独评估，不能由“迁移成功”推导为已验证。

全托曾做精确增量计划、数据指纹比对和独立 fresh dry 验证；这些原则可借鉴，七表/六序列等实例数量及 SQL 不适用于半托。

### 第三步：搭新云入口、受限出口和专属隧道

- 新云只增加半托专属配置，监听回环地址；业务和数据库端口不直接开放公网。
- 飞牛主动连接新云：LocalForward 服务于固定出口，RemoteForward 服务于公网入站；限制 permitopen/permitlisten，固定主机指纹，关闭交互登录能力。
- 隧道由 systemd 管理重连，设置 ExitOnForwardFailure 和保活；先证明监听来自正确的新隧道，避免命中遗留进程。
- CONNECT relay 只允许所需上游。全托服务端只放行 `openapi.sheincorp.com:443`；半托不能照抄：还涉及授权域名 `openapi-sem.sheincorp.com:443`（测试环境另有 `openapi-test01.sheincorp.cn` / `openapi-sem-test01.dotfashion.cn`）。半托方案（`semi-managed-fnos-migration-plan-20260915.md` §1.8、§6）按“同时放行 `openapi.sheincorp.com:443` 与 `openapi-sem.sheincorp.com:443`”执行，只放行 API 域名属于已知遗漏点。
- 半托现状的域名分工（代码事实）：授权域名只用于生成浏览器打开的 empower 授权页（`lib/shein_openapi_client.mjs` 的 `SHEIN_OPENAPI_AUTH_HOSTS.prod`），服务端换票 `getByToken` 走的是 `SHEIN_OPENAPI_BASE_URLS.prodSemiManaged` = `openapi.sheincorp.com`。因此“relay 同时放行授权域名”成立的前提，是授权页那一侧的流量也走固定出口；若半托浏览器 lane 保持直连（直接出办公室 IP），服务端 relay 严格只需要 API 域名。阶段 3 定允许列表前先把这条对齐。
- 现有 relay 把允许的 authority 写死在代码里：`src/openapi/connect-relay.mjs` 的 `SHEIN_OPENAPI_CONNECT_AUTHORITY` 只有 `openapi.sheincorp.com:443`，`scripts/serve_shein_openapi_connect_relay.mjs` 启动日志和 `tests/openapi/connect-relay.test.mjs` 也按单 authority 断言。要放行第二个域名必须改代码或另起一个 relay 实例，部署侧加配置不生效。
- 保留原反代的签名头、请求体、Host、WebSocket、超时、限流与日志脱敏语义；不能仅搬首页路由。
- 对共享代理先备份、锁定哈希、校验候选配置、比较其他路由，再窄范围 reload。

验收：本地业务端点、云回环端点、新 IP + 正确域名/SNI 的 HTTPS 分层通过。可采用 curl 的 `--resolve <半托域名>:443:43.165.185.3` 测试，不能用 `-k` 掩盖证书问题。

### 第四步：白名单先加后切，逐店测试真实认证

- 盘点半托每家店对应的应用/主体和白名单管理入口；不要假定全托的 17 个主体覆盖半托全部应用。
- 使用店铺独立持久 Profile，确认身份后添加 `43.165.185.3`，保留原 IP；保存后刷新回读。关闭仅本任务启动的浏览器，保留登录资料。
- 从飞牛以真实业务用户、真实客户端和现有资源门禁，逐店执行最小只读 OpenAPI 探针。
- 先测试候选代理，再切正式配置，切后再次逐店验证；保存逐店结果和配置指纹，不在报告中输出凭据。

全托切换前后均 25/25 店认证通过。TLS 成功、根路径返回 401，只能证明可达，不能证明应用认证或白名单成功。

### 第五步：切数据和业务执行权，保证单边运行

- 按计划停旧调度/消费者，确认无在途写入或锁未释放，完成最终数据追平并记录基线。
- 只在基线通过后启用飞牛服务和必要门禁，再切业务路由；若需要持续接收回调，事先定义维护窗口内的接收/暂存/重试路径。
- 迁移原有排班，不新建重复 timer/cron。确认旧侧 inactive/disabled、新侧实际 active；oneshot 必须看实际 InvocationID、执行时间及终态。
- 正式 OpenAPI 配置要强制经过指定代理，代理不可用时拒绝请求，不能静默回退办公室公网 IP。必须确认半托客户端实现支持此约束，仅设置环境变量不够。
- 授权服务、续期服务和后台任务都要纳入出口核查；检查实际进程环境和连接，不只检查配置文件。

验收：只有新侧产生预期新增数据或执行任务；至少一个真实业务周期完成，页面读取的新数据与任务结果对应。原有 PARTIAL/DEGRADED 不算本次修复，也不能当成零。

### 第六步：DNS 与自动证书

- 确认域名归属、权威 NS、A/AAAA/CNAME 和代理模式。仅更新目标业务所需记录，避免影响其他子域名。
- 多个公共解析器及实际来源网络交叉验证；既测正常域名解析，也测绑定新 IP 的 HTTPS。
- 配好自动证书管理，验证日志实际签发成功和公网握手提供的新证书；确认存储持久化及续期所需网络条件。
- 域名/NS 同时迁移时，旧 DNS 区能修改则同步更新；否则保留旧入口到新入口的兼容转发，保持正确 SNI 和证书校验。

全托当时 A TTL=300 秒，但部分解析器仍看到旧 NS，NS TTL=43200 秒。不能认为“改 A 后五分钟全部生效”，也不能把 12 小时当作所有解析器严格收敛上限。

### 第七步：真实链路终验

- Portal：实际登录、主要页面和数据读取，而不仅是健康检查。
- OpenAPI：逐店只读认证和实际出口正确；数据完整性另行判断。
- Webhook（若半托使用）：真实平台投递 → 新云日志 → 验签后 receipt → job → 业务事件或对应终态，逐条关联核对；验证重复投递不重复执行业务。
- 调度：实际触发时间、唯一运行实例、终态和物化结果一致；不能用尚未运行的 ExecMainStatus=0 证明成功。
- 会话和授权：既有会话可用、续期路径正确；新授权换票只有实际验证后才标通过。全托 9 月 8 日仅验证授权页面可用和出口环境，没有在该次收尾重做新授权换票。
- 回归：共享云上其他项目、现有全托入口和任务仍正常。

全托 9 月 8 日退役旧隧道后收到的两条真实回调均处理成功，重复投递收敛，receipt/job/event 无缺失。健康端点 200 无法替代这些证据。

### 第八步：退役旧组件并交付证据

- 停旧隧道前先检查业务 unit 的 Requires/After 等依赖，切换到新隧道并回读有效配置。
- 只停半托专属服务和移除半托专属站点；共享 Caddy/Nginx/HAProxy 保留。验证旧监听消失、新入口仍正常。
- DNS 来源已收敛且旧入口不再承载必要流量后，再移除兼容路由。忘记删除通常不影响新链路，但旧服务器退役前仍须确认没有其他业务依赖。
- 撤销本次临时管理员凭据，验证新连接被拒绝、永久隧道仍正常；保留原管理员权限。
- 数据删除和旧服务器销毁应单独确认精确范围。新侧产生数据后，回滚需要追平新增数据，不能直接启动旧数据库当作无损恢复。
- 交付配置备份/哈希、逐店验收、数据库对账、真实回调证据、服务及调度状态、残留项和回滚步骤。证据至少保留在不随旧机销毁而丢失的位置。
